# 근무표 PWA 서비스 워커 선택과 검증

## 확인한 경합

기존 코드는 Flutter 첫 프레임에서 근무표 워커 등록을 시작하지만, `offlineReady()`는 별도로 `navigator.serviceWorker.ready`를 읽었습니다. 근무표 등록 전에 상위 TripGrid 등록이 활성 상태이면 이 Promise가 상위 등록으로 해소될 수 있습니다. `ready`는 한 번 해소된 등록을 재사용하므로 나중에 근무표 워커가 활성화되어도 상태 확인이 TripGrid로 향할 수 있습니다. TripGrid는 `OFFLINE_STATUS`를 처리하지 않으므로 기존 30초 타임아웃 후 `false`가 됩니다. 이는 코드상 가능한 경합이며 실제 iPhone에서 발생했다는 증거는 아닙니다.

근거: [Service Workers 명세의 ready](https://w3c.github.io/ServiceWorker/#navigator-service-worker-ready), [등록 범위 선택](https://w3c.github.io/ServiceWorker/#scope-match-algorithm).

## 변경된 순서

1. 첫 프레임과 상태 확인이 동일한 등록 Promise를 공유합니다. 첫 프레임 이전 상태 확인도 직접 등록을 시작합니다.
2. `/shift-schedule-duo/sw.js`와 `/shift-schedule-duo/` scope를 명시합니다. 반환된 scope와 활성 워커의 scriptURL이 정확히 일치해야 합니다.
3. 해당 등록의 `installing`, `waiting`, `active` 상태와 `updatefound`를 관찰합니다. `active`가 있어도 `activating`이면 기다리고 `activated`일 때만 메시지를 보냅니다.
4. `OFFLINE_STATUS`는 그 활성 워커에 직접 전송합니다. `navigator.serviceWorker.ready`나 페이지의 현재 controller로 워커를 선택하지 않습니다.
5. 등록부터 응답까지 최대 30초, 활성 워커의 응답은 최대 3초를 기다립니다. 먼저 도달하는 제한을 적용합니다. 종료 시 타이머·이벤트 리스너·메시지 포트를 정리하며 늦게 끝난 등록은 메시지를 보내지 않습니다.
6. 등록 실패 시 다음 확인에서 재등록할 수 있습니다. 설치/응답 타임아웃의 `false`는 이번 확인에서 준비를 입증하지 못했다는 뜻이며 영구 오류를 뜻하지 않습니다.

기존 활성 근무표 워커가 있고 새 버전이 설치/대기 중이면 현재 활성 버전의 캐시를 확인합니다. 새 버전을 강제로 활성화하거나 화면을 자동으로 새로고침하지 않습니다. 전체 FILES 항목을 확인하는 기존 워커 로직은 유지하고, 변경된 app.js가 캐시에 반영되도록 캐시 VERSION을 갱신했습니다.

TripGrid의 워커·캐시 정책, Flutter 코드, localStorage/IndexedDB의 근무표 데이터와 백업 형식은 변경하지 않았습니다. 기존 클라이언트가 모두 닫힌 후 새 워커가 활성화되면 기존 정책대로 근무표의 이전 셸 캐시만 정리됩니다.

## 자동 검증

`node --test tests/shift-offline.test.cjs`: 20개 통과.

Node VM에서 실제 app.js와 두 sw.js를 실행하며 브라우저 API·시간·저장소를 모의합니다. 첫 프레임 전 호출, 동시 호출, 설치→활성화, updatefound, 기존 활성/새 대기 워커, 잘못된 scope/스크립트 거부, 등록 실패 후 재시도, 설치 실패, 30초 전체 제한, 3초 응답 제한, 늦은 등록/활성화, 전송 오류, 잘못된 응답, 미지원 환경을 검사합니다.

캐시 전체/일부 누락/전체 삭제/접근 오류, 설치 중 자산 다운로드 실패, 범위별 이전 캐시 정리, 오프라인 셸 응답, TripGrid 경로 분리와 기존 탐색 처리도 검사합니다. 목록의 모든 캐시 자산이 저장소에 있는지 확인합니다. JavaScript 구문 검사와 `git diff --check`도 통과했습니다.

실제 브라우저 설치 파일 다운로드 실패로 브라우저 엔진 통합 검사는 수행하지 못했습니다. 아래 iPhone 검증은 별도로 필요합니다.

## iPhone 확인 조건

Safari 탭과 홈 화면 PWA에서 각각 확인합니다. 기존 사용자 데이터가 있는 기기는 웹사이트 데이터 삭제나 워커 등록 해제를 하지 않고 업데이트 검사를 진행합니다. 신규 설치 조건은 데이터가 없는 별도 기기/프로필에서 확인합니다.

| 조건 | 확인할 결과 |
| --- | --- |
| 아무 워커도 없는 상태에서 근무표 최초 실행 | 온라인에서 셸 저장 완료 후 준비 상태가 정상으로 바뀌며, 앱 종료→비행기 모드→재실행 시 근무표가 열림 |
| TripGrid를 먼저 실행하여 상위 워커만 활성화한 뒤 근무표 최초 실행 | 근무표 등록과 활성화를 기다려 정상 판정하며 상위 워커 때문에 30초 동안 멈추지 않음 |
| 두 앱이 설치된 상태에서 각 앱을 번갈아 실행 | 근무표와 TripGrid가 각자의 화면·캐시를 사용하며 서로의 셸로 열리지 않음 |
| 느린 연결 또는 설치 중 일시적인 연결 끊김 | 설치 완료 전 준비 완료로 표시되지 않음. 최대 30초 후 미확인으로 종료하고, 연결 복구 후 다시 열어 확인하면 준비 상태로 회복 가능 |
| 온라인에서 준비 완료 확인 후 앱을 완전히 종료하고 오프라인 실행 | 근무표·메모·급여 기록과 TripGrid 기존 데이터가 유지되고 각 앱의 캐시 화면이 열림 |
| 기존 근무표 탭을 유지한 채 새 버전 배포 후 재접속 | 기존 활성 버전으로 계속 동작. 근무표 탭/PWA를 모두 닫고 온라인으로 다시 열면 새 버전이 활성화되어 재검사 가능 |
| 시험용 환경에서 근무표 셸 캐시 자산 하나 또는 해당 셸 캐시만 삭제 | 활성 워커가 남아 있어도 준비 판정은 실패. 데이터 저장소와 TripGrid 캐시는 유지됨 |
| 시험용 워커의 OFFLINE_STATUS 응답을 막음 | 활성화 후 최대 3초 안에 미확인 종료. 설치 대기와 합쳐 30초를 넘기지 않음 |

일반 기기 확인에는 명령 실행이 필요하지 않습니다. 캐시 삭제·응답 차단은 개발자 도구를 사용할 수 있는 시험용 환경에 한정합니다. 배포 직후 기존 오프라인 앱은 이전 캐시의 app.js를 사용할 수 있으므로, 온라인에서 업데이트를 받은 뒤 관련 탭과 PWA를 모두 닫고 재실행하여 새 버전 검증을 진행합니다.
